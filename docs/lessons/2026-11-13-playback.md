# 经验：HGhub 播放修复（2026-11-12 → 11-13）

> 一次「客户端没坏、是站点换协议」的完整排查，以及随后的一轮体验优化。
> 结论按可复用性排序；每条都注明当初是怎么被证伪/证实的。

## 1. 症状落在客户端，根因常在协议层

用户看到的是「视频暂时无法加载 / 暂无播放地址」，第一反应是字段改名、取址逻辑漏判。
真实原因是站点在 2026-11-12 把 `/api/**` 整体换成了 `dx150-edge-v1` 加密信封，
旧明文 `POST /api/edge/request` 直接回 `{"error":"请求无法处理"}`，
`GET /api/videos/{id}/play` 仍返回 200、`status=1`，但 `video_url` 恒空。

**可复用做法**：报错文案只描述现象。「取不到地址」先分三种可能——字段变、资源没、通道换了；
判据是**直接抓线上前端 JS**（站点被墙就走本机代理抓），比猜字段快一个数量级。
抓到的 JS 里 `window.__cloudfrontCompat.encryptedAPIRoutes` 直接给出 124 条路由映射。

## 2. 「deprecated」不等于「不生效」

hls.js 1.6.15 里 `manifestLoadingTimeOut` / `fragLoadingTimeOut` / `*MaxRetry` 都标了 `@deprecated`，
但 `src/config.ts:659-697` 有兼容层：只要没显式设置 `manifestLoadPolicy` / `fragLoadPolicy`，
旧字段会被写进 `maxLoadTimeMs` / `maxTimeToFirstByteMs` / `timeoutRetry`。

一次独立复审据此判了 Blocker（「死配置，什么都没改」）。读源码后证伪。
**教训**：涉及第三方库行为，判断依据是 `node_modules` 里的实现，不是类型注释，也不是复审意见。

## 3. 网络型客户端必须能配代理，且配置要可失败

国区网络访问 `huangguoai.com` 443 被 reset，手机 4G 超时、开 VPN 正常。
客户端内置代理支持时踩到两个坑：

- 只认 `/data/data/<pkg>/files/proxy.txt`（需 root）→ 补 `/sdcard/Android/data/<pkg>/files/proxy.txt`。
- 非法代理串 `Proxy::all` 失败后仍把 `PROXY` 写成 `Some(..)`，界面上以为在走代理，实际直连。
  修法是**先验证再提交**，失败不写状态。
- `build_client().expect()` 在持写锁时 panic 会毒化锁，此后永远换不了代理且不报错；
  而 `reqwest::Client::new()` 本身也是 `expect`（TLS 初始化失败就 panic），拿它当兜底等于没兜底。

**结构性结论**：代理值和客户端必须放在**同一个 `RwLock` 里的同一个 struct**，一起换。
拆成两把锁或两个全局，无论怎么排写入顺序，都会出现「`current_proxy()` 说走代理、实际直连」的窗口；
更隐蔽的是把探测逻辑写进 `Lazy` 初始化体——初始化会在 `set_proxy` 强制求值时反向覆盖刚写入的值。

另外：文件里残留的死代理要**启动自检**（代理不通 + 直连能通 → 自动回退直连），
否则调试留的一条 `proxy.txt` 会让整条链路（含分片下载）指向死端口，而界面上没有任何痕迹。

## 4. MIUI `Invalid apk`（-111）先查 guardprovider

`INSTALL_FAILED_USER_RESTRICTED: Invalid apk` 在 Redmi K60 / HyperOS 上，
日志里是 `E/AdbInstallActivity: call guard provider to parse apk failed: Unknown authority guard`。
`com.miui.guardprovider` 被卸载 → MIUI 安装器解析不了**新装** APK（已装应用更新不走这条路）。

```
adb shell pm install-existing --user 0 com.miui.guardprovider
```

修完若报 `Install canceled by user`，是锁屏导致确认页弹不出来，解锁重试。

排除顺序（都实测过）：签名方案组合 → 包名 → targetSdk（与能装的 DeepSeek 对比）→ 证书（换证书重签仍失败、
用我们的证书重签 DeepSeek 能得到 `UPDATE_INCOMPATIBLE`，说明签名链正常）→ 安装器身份。
**拿到安装器日志比逐个变量试快得多。**

## 5. CI 出包的三个固定坑

- workflow 配了 concurrency：**新 run 会 cancel 旧 run**，`gh run watch` 因此常返回 1，判定以 `gh run list` 的 `conclusion` 为准。
- artifact 下载必须带 `--proxy http://127.0.0.1:7890`，直连 25KB/s；artifact zip **不支持 Range**，别用 `-C -`。
- `git push` 到 github.com 不通时用 API 建 blob→tree→commit→PATCH ref；脚本必须存成 UTF-8 BOM，
  commit message 用 `[string](Get-Content -Raw) | ConvertTo-Json`，别对整段 commit JSON 做 `ConvertFrom-Json`。

## 6. 播放体验的性价比排序（本轮实测）

| 优化 | 效果 |
| --- | --- |
| 切集复用 hls 实例 + 地址缓存 | 首帧从「重新起播」变成缓存命中 ~33ms（冷起 670–970ms） |
| 预取下一集地址 + 预热 m3u8 | 切换集几乎无等待 |
| 播放列表缓存键去掉 `auth_key` | 重看同集不再重拉 m3u8（保留 `v` 防清晰度串台） |
| `testBandwidth:false` + 低初始码率 | 首帧更早出画 |
| 进度条热区 28px（视觉仍细） | 手指能按住，且拖动中只更新预览、松手才 seek |
| 超时/重试收紧（manifest 10s×2） | 断流时更快进入自愈，不再干等 |

## 7. 复审要会用，也要敢驳

两轮 reviewer 各给出过一条错误结论（「吃瓜视频源丢失是本次回归」「hls 超时是死配置」），
都用 `git show <base>:<file>` 与库源码证伪。另一类复审意见是**方向对但位置错**：它看到了「两种状态会不一致」，给出的修法是补校验；
真正的问题是结构——两个全局变量永远无法原子地一起换。这类要顺着它的证据往下推一层，改结构而不是加校验。

复审的价值在于覆盖面（生命周期、并发、兼容、跨语言边界），不在于它一定对；
**每条 Blocker 都要自己复现或证伪**，否则会按错误结论改代码。
